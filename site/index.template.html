What the ZIP contains

An unmanaged Power Platform solution named poc_PowerBIQueryRuntime, version 1.0.0.0. It contains the native metadata, generated DAX, advice and error topics, a Power BI connection reference, hidden variables and 129 configuration environment definitions.

What it excludes

No source tenant bindings, current environment values, credentials, channel registration, private model metadata, workspace or dataset IDs, raw transcripts, customer data, cloud flows, custom connectors, MCP server or Fabric data agent.

How it works

Architecture: native topics around one Power BI connector action

The deployed design is: question → authorised metadata retrieval → LLM-generated table expression → validated execution envelope → Power BI as the caller → explained answer. Topics control the workflow; the embedded Run a query against a dataset connector action executes the DAX.

The connector action is inside the topics. It is not a separate tool per question, a hosted Python service, a Fabric data agent or the hosted Power BI MCP server.

Metadata

Owner-prepared snapshot; requesting-user schema visibility probe before disclosure. The primary snapshot contains 21 tables, 244 columns, 166 measure names and 13 relationships.

Generated query

The runtime accepts a DAX table expression plus aliases, ordering and optional date expressions, not an arbitrary full script. Limits are up to 100 rows, 16 columns and 256 characters per text cell.

Advice path

The advice topic compiles and explains proposed DAX without executing the business query. Metadata authorisation may still probe Power BI.

Authentication

Power BI runs as the signed-in requester

The Power BI connector operation is ExecuteDatasetQuery. In the topic action, query text is bound to Topic.generatedDax, output rows are dynamic Any, null omission is explicit and the connection stays in Invoker mode with a blank impersonated user.

The agent does not grant model access

Runtime users still need suitable Power BI Read and Build permissions, any applicable RLS/OLS access and their own connection consent. Build permission is more powerful than report viewing. Agent instructions are not an authorisation boundary.

Prerequisites

Permissions, licensing and policy checks

  • Copilot Studio authoring/runtime licensing and an appropriate Power Platform environment.
  • Power BI licensing appropriate to the model and workspace.
  • An authenticated user with Read and Build access to the semantic model.
  • The tenant Dataset Execute Queries REST API setting enabled.
  • Power Platform data policies that permit the required Power BI connector.
  • A governed, current metadata snapshot and a Power BI connection configured for end-user / Invoker execution.
  • An already authorised model owner for definition preparation or refresh; do not grant model-write access to every agent user.

Step by step

Import and configure the runtime

  1. Import first, without activation

    Choose a fresh approved sandbox. Import PowerBIQueryRuntime_unmanaged.zip directly. The solution creates an unpublished, unconfigured agent and should not be treated as a working M365 deployment.

  2. Bind the Power BI connection

    Map the poc_PowerBIQueryRuntime_PowerBI connection reference to an approved destination Power BI connection. Keep Invoker / user credentials and blank impersonation.

  3. Prepare model metadata privately

    Install declared dependencies, copy the example resource and target files into private locations, and run the owner preparation helper against your approved workspace and dataset. Review business definitions separately.

  4. Load configuration values

    The helper prepares a bounded JSON document, splits it across 128 data slots plus a manifest, checks the destination and writes only current environment-variable values in one verified operation.

  5. Publish and test separately

    Changing values alone does not update an already published runtime. Publish in Studio, start a new conversation and smoke-test unconfigured state, metadata, query, advice, limits, denied identities and stale configuration.

  6. Share through approved channels

    Configure and share the M365 Copilot channel through your tenant's approval process. Authentication, connection consent, audience and channel registration are not delivered as a finished deployment in the ZIP.

Native capabilities

Topics, contracts and connector fields

Complete instructions and topic YAML

The downloadable YAML files are complete reference files, not snippets and not the private configured demo. They use synthetic metadata and placeholders; generate model-specific versions before deployment.

Get model metadata

Generative topic. Validates the model alias, probes schema visibility as the requester, then returns governed metadata.

Run generated DAX

Generative topic. Requires the current-turn metadata gate, validates newly authored DAX and executes it through the embedded Power BI action.

Compile DAX advice

Generative topic. Uses the same expression contract but does not execute the proposed business query.

Generated query error

OnError topic. Reports the actual error and stops rather than fabricating an answer.

Example conversations

Ask for an answer, or ask how

The test model contains agent inventory, creator/ownership and usage data, which is why examples ask about agent rankings, creators and interactions. The agent runs DAX against the semantic model, not report visuals.

Example prompts

  • Give me the top 100 agents by usage.
  • Give me the top agents and their usage over the last 30 days.
  • Explain how to rank agents by Interactions in DAX using this model. Explain filter context and do not run it yet.

Unsupported requests should be explicit. Do not substitute a different measure when the requested metric is missing.

Scope and limits

Reusable execution is not automatic model understanding

One configured model alias

Only alias primary is configured. Automatic multi-model discovery, routing and cross-model interpretation remain separate work.

Metadata is not semantics

The snapshot is not live per-turn discovery or complete business meaning. Measure definitions, date logic, blanks and report filters still require review.

Execution is not accuracy

A successful DAX call proves the query ran, not that the question was understood, the right measure was used, or the values were independently audited.

The second-model experiment retrieved a different model definition with 78 tables, 694 columns, 17 measures and 79 relationships, but it was not wired into the agent and does not prove automatic business understanding.

Verification boundaries

Evidence without overclaiming

Observed and separately checked

  • Constant-only and varied direct DAX queries executed.
  • Original top-100 membership/order regression passed.
  • Published M365 UI captures show top-20 ranking, top-five follow-up and unexecuted DAX advice.
  • Offline Python, client harness and synthetic native checks exercise source and transport boundaries.

Not proven by the site

  • Universal query correctness.
  • Independently audited displayed values.
  • Automatic schema refresh or multi-model routing.
  • Configured behaviour of your imported copy before you bind, configure, publish and test it.
